# Bring PGP back, I/O-free

Restored the sign, encrypt, decrypt and verify support the pre-2.0 pimalaya/core/mml carried, on the coroutine seam rather than the async backend abstraction it used. One new spec capability: pgp.

The old design was `Pgp`, an enum of three backends (native, commands, gpg) behind `async fn`, which forced async through the entire compiler and interpreter. Only gpg survives: native needed a key-discovery stack including HTTP, and a single command template cannot express per-recipient key selection. Removing async from a text-processing library, rather than pluggability, is what the I/O-free shape buys.

The grammar came back unchanged from the legacy implementation: `sign`, `encrypt`, `sender` and `recipients` as properties on `<#part>` and `<#multipart>`, `pgpmime` the only accepted value. There is no `<#secure>` directive and never was one here.

Two machines carry the suspension. The compiler flattens the parsed tree into a post-order worklist, so a part is signed or encrypted only once everything it contains is final; this was possible only after `compile_part` was made to return `MimePart<'static>`, which took three lines and removed the borrow problem entirely. The interpreter iterates a queue of layers, each owning its bytes through a `Cow` behind ouroboros, mirroring what pimalaya/core/email did for the same reason. Neither recurses across a suspension.

One behaviour deliberately diverges from the legacy implementation. `try_encrypt_part` and `try_sign_part` logged a debug and returned the cleartext part when PGP failed or was unconfigured, so a message marked `encrypt=pgpmime` could go out unencrypted. Here an unavailable or failed answer aborts the compilation. Reading still degrades visibly, since showing an unresolved marker loses nothing.

Reply and forward stopped interpreting their source. The builders now expose `quote_options()` and take the rendered quote as an argument, which is the only way a caller can drive the coroutine and decrypt an encrypted thread before quoting it. Previously such a thread quoted as `<#part type=application/pgp-encrypted>`.

The signer resolves from the part's `sender`, falling back to the message `From`. No configuration key was added: `From` already comes from the account, and a third place to look would only obscure which key signed.

`pgp-gpg` is off by default and pulls gpgme, libgpg-error and pkg-config into the nix package only when enabled; the dev shell carries them unconditionally, plus zlib on `LD_LIBRARY_PATH` because linking gpgme pulls it into the build script too.

The end-to-end suite generates its GPG store per run. The checked-in `tests/gpg-home` fixture in pimalaya/core/mml carried keys that expired on 2025-08-04, so that suite had been silently dead for a year. Eleven tests cover the four actions, the nesting order, nested encrypted layers, quoting an encrypted thread, and the failure paths. Verified live against a real published key as well as generated ones.

The verify verdict reaches the CLI as a distinct exit code: `interpret` exits 0 with no signature or a valid one, 2 with an invalid one, and 1 on any other failure. The message renders either way, since a bad signature is a reason to distrust it rather than a reason to hide it. The same verdicts ride the printed value, so `--json` reports a `signatures` array while the plain rendering stays the raw MML. Nothing goes to stderr, which carries logs alone.
